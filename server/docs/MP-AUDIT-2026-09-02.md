# Multiplayer audit — the mp912026 overhaul

Three independent read-only reviews (server authority, Lua peer/client, plan-vs-code) plus a
manual pass. This records every finding, its disposition, and the evidence. Fixes are on the
branch; nothing is pushed.

## Bugs found and FIXED

| # | Severity | Bug | Fix |
|---|---|---|---|
| 1 | critical | **Respawn death loop.** A driving player's avatar dies on the peer; the respawn plugin resurrects the *player* only; the avatar stays dead and its 3 s bar report (hp 0) re-kills the player forever. | Server relays `PlayerResurrect` → `AvatarResurrect` to the peer (server.ts sendEvent hook), opens a resurrect window (`resurrectedAt`, `RESURRECT_GRACE_MS = 6 s`) during which hp≤0 peer reports are ignored, and clears `peerStatsAt` so the client's restored bars rule until the fresh body reports. Peer resurrects + repositions the avatar (`MP_AvatarResurrect`). |
| 2 | critical | **Peer crash orphaned every anchored cell.** Disconnect released only the 3×3 around the peer's avatar; every other anchored cell kept a dead holder id, and a restarted peer could never re-take them (onEnter only *informs* when a foreign holder exists). | `authorityLeaveAll` for a system player now releases `authority.cellsHeldBy(id)` — the peer's whole footprint. |
| 3 | critical | **No holder-loss signal.** When the holder left, clients kept a stale `holderOfCell`, so melee was cancelled-not-forwarded forever and NPC puppets froze (AI off, no poses). | Server `info(..., holderId=undefined)` on loss; client `MP_ActorAuthorityInfo` with no holder clears the mirror and `detachActorPuppetsInCell` so local AI resumes (degraded mode). |
| 4 | high | **Melee double-damage window.** Before `ActorAuthorityInfo` arrived, `hasHolder` was false → a real swing forwarded via the relay AND the peer's avatar hit natively. | A real (non-`mpTest`) client swing is now *always* cancel-only (`combat.onPuppetHit`): the peer's avatar computes every melee. The relay survives only for `mpTest` hooks (s51/s58) and magic. |
| 5 | high | **Two system peers = split brain.** Input/PvP went to the first system peer in roster order; anchors/authority to the supervisor's; both streamed poses (last-writer-wins jitter). | One `worldPeer()` resolver (supervisor's spawn, else lowest id) used by all six call sites; avatar/stat/item batches from any *other* system peer are rejected (`avatarBatchRejected{not_world_peer}`). |
| 6 | high | **PvP-off servers still took PvP damage** on the peer (avatar-vs-avatar melee resolves natively regardless of the flag). | Fixed in Tier-2 below: an `I.Combat` veto on the avatar, driven by an `mpAvatarPolicy` push. |
| 7 | high | **Standalone stack lost peer-written quest globals.** `journalTarget(peer)` on an owner-less server resolved to the peer's ephemeral doc; relayed live, lost on relog. | `globalVar` for a system sender with no owner persists to every in-world human's doc (each got the relay) and returns. |
| 8 | medium | **Writer flapping.** The 300 ms `peerPoseAt` gate vs the 5 s driving gate let a peer hitch >300 ms alternate client/peer as the pose writer. | One exported `PEER_POSE_FRESH_MS = 2 s` (players.ts) for handleMove + the state-batch tick; the avatar-pose *acceptance* window also moved to 2 s so a starved browser's coasting avatar stops gating its own real frames (the s69 statue). |

| 11 | medium | **`mayJoinWorld` cap counted in-world, not authed** — ten friends dialling in one second all passed a cap none had crossed. | `roster.humanCount < 32` (authed), matching the hello-time full check. |
| 12 | medium | **Equipment placeholder ban was missing** — `pushEquipmentToPuppet` substituted a stand-in for an unresolvable *weapon* on the peer (wrong damage). | On the peer the slot is left empty, logged, and `avatarUnresolvable` set — same ban as the inventory path. |
| 13 | low | **A throwing frame from the world peer dropped the simulator.** `onMessage`'s catch disconnects the sender; for the peer that freezes every cell. | System peers are logged/counted but not disconnected on `internal_error`. |
| 14 | low | **A superseded/never-in-world session armed the owner grace / mis-fired onWorldEmpty.** | `onWorldEmpty` counts humans, not the peer. *(Grace-on-supersede is Tier-2.)* |

## NOT bugs (verified, left as-is)

- **Melee skill progression under 4C.** `Npc::hit` awards `skillUsageSucceeded` (npc.cpp:673)
  *before* the Lua `Hit` veto (npc.cpp:707), and only for `ptr == getPlayer()`. So on the
  attacker's client the skill is credited before puppet.lua cancels the damage — progression
  is preserved. No fix needed.
- **Globals echo loop.** `relayAll(exceptId)` excludes the sender; the client applier writes
  the cache before the engine and returns on no-change. No loop.
- **Malformed LSER.** Every handler validates with `tbl`/`finite`/`recordId` before use.

## Pass 2 - reviewing the fixes, and the subsystems pass 1 never opened

Three more reviews: an adversarial read of the pass-1 diff, and fresh eyes on persistence,
gateway, session and social. **Two of pass 1's own "critical fixes" turned out to be fake.**

| Severity | Bug | Fix |
|---|---|---|
| critical | **The respawn fix did nothing.** It called `types.Actor.resurrect`, which does not exist in the Lua API (`mp.resurrect` is player-only, and says so). The `pcall` swallowed the error, so the avatar stayed a CORPSE that merely *reported* healthy bars: no AI, no controls, no melee, for every player who died. The Lua suite passed 61/0 because nothing exercised death on the peer. | The peer replaces the body (`despawnPuppet` + `spawnPuppet`), which also re-applies the character doc. New scenario **s77-death-respawn** covers the chain and asserts the player is still alive after the window. |
| critical | **The holder-loss signal was never sent.** Pass 1 widened `info()` to carry "no holder" and taught the client to detach on it, but no call site ever passed it, so the detach was unreachable. Compounded by the pass-1 melee change (a real swing is cancel-only whenever a holder is *believed* to exist): during a peer outage **melee did nothing at all, permanently**. | `Authority.onLeave`'s dormant branch informs every occupant. Test added. |
| high | **The heal cap trusted the client's claimed base.** `Math.min(v.c, v.b)` on the untrusted body: a client asserting `{c: 99999, b: 99999}` was stored at ten times its real maximum. | Cap against the STORED base; the rate budget stays on top. |
| high | **Bans were a boot-time snapshot.** `bans.db` is shared by every world process, but reads hit an in-memory map loaded at construction, so a ban issued in one world was ignored by every world already running. | Read through to the database. |
| high | **Account erasure never opened `social.sqlite`** - friends, blocks, requests, invites, mutes, presence and the person's own chat lines survived an erasure the privacy doc calls complete. The completeness test passed because its **hand-maintained file list omitted that database**. | `eraseSocialDb` covers all nine tables; the test now discovers every db in the directory. |
| high | **A stopping world was handed to joining players** - the directory spliced a socket into a draining process. | Refuse while `stopping`. |
| high | **Cross-process `ALTER TABLE` race** killed a world at boot on the deploy that introduced a column. | The duplicate-column loser is tolerated. |
| high | **Epoch churn (pass-1 regression).** The peer-footprint release shared a path with the peer's ordinary cell change, so every avatar move dropped all anchored cells and forced a full actor re-sync everywhere. | Disconnect and cell-change split into separate methods. |
| medium | `allocNetId` could reissue the on-disk ceiling after a crash (duplicate netIds); the template shed stripped the equipped weapon the equipment push had fabricated; internal-error immunity keyed off an unauthenticated Hello claim; the owner grace never armed (pass-1 regression: existence vs identity). | All fixed. |
| low | `releaseCached` could discard an update landing during its own flush; `onWorldEmpty` counted bots; standalone quest-globals reached bot docs. | Fixed. |

**Verified clean by pass 2:** the teleport gate cannot wedge a player into permanent client
authority; `onPuppetSpellHit` is a separate path; the PvP veto's late registration really does
run first and cancel; resume tickets are single-use with ban enforcement; `openDb`'s
`BEGIN IMMEDIATE` handles concurrent world boots; `/saves` has no cross-account read.

**The lesson worth keeping:** a green suite proved nothing about a call to a function that does
not exist. Every fix touching peer-side Lua needs a scenario that exercises it - the unit tiers
cannot see it.

## Pass 3 - the one the harness found

| Severity | Bug | Fix |
|---|---|---|
| critical | **The engine owns the `MP_` prefix.** `mwmp/netmanager.cpp` dispatches every event-tier message as `addGlobalEvent({"MP_" + name})`, so the server must send the BARE name. `playerstate.ts` sent `'MP_SelfStats'` and `'MP_SelfItemStates'`, which arrived looking for handlers called `MP_MP_SelfStats` / `MP_MP_SelfItemStates`. Neither exists, so **every health/magicka/fatigue bar and every item-state update was dropped on the floor for every real player, for as long as Phase 4A/4D have existed.** | Send bare names. `test/eventnames.test.ts` is a source-text invariant forbidding the `MP_` prefix on any `sendEvent()` in `src/`; verified it fails when the bug is reintroduced. |

Nothing could catch this on the server side: TypeScript sees a string, the Lua handler exists
and reads correctly, and the server tests assert on RAW wire names off a `TestClient` that does
no prefixing at all. A feature whose events reached **zero** players had a fully green suite
behind it - the same shape as the fake resurrect in pass 2. **s77 found it**, failing on "the
peer reports this player's bars" long before it got near the death step it was written for.

### Two more, once the bars stopped hiding everything behind them

| Severity | Bug | Fix |
|---|---|---|
| high | **`mp.resurrect` broke two vanilla subsystems on every respawn.** It resumes the world with `StateManager::resumeGame()` from inside a `DelayedAction`; that calls `gameLoaded()`, which notifies menu scripts, whose `onStateChanged` handlers queue delayed actions of their own — which `addAction` forbids mid-pass. `scripts/omw/settings/menu.lua` and `scripts/omw/console/menu.lua` threw on every death, and a throwing handler disables its whole subsystem for the rest of the session. | `LuaManager` defers the menu `stateChanged()` notification to the end of the action pass (`notifyMenuStateChanged`). The state change is real either way; only the notification waits. Covers every engine path that changes state from an action, not just ours. |
| high (harness) | **A one-shot command issued before the client could act on it.** `walk:` carries a deadline: `player.lua` drops it if the player cannot move yet (a fresh client is still finishing chargen), and the command then expires unused. s22 issued its walk the instant `launchClient()` returned and then spent 120 s waiting for movement it had already thrown away. | `handle.walk()` reissues the command until the player has actually covered the distance the caller asked for. A slot-drain wait was tried alongside it and REMOVED: it was built on the wrong theory (the `pause:` commands it was meant to protect are no-ops), it fixed nothing observed, and it put an extra round trip on every command write — including s58's 1.5 s swing loop, which then timed out in-suite while passing solo. |

The s22 failure is worth remembering as a shape, and so is the first attempt at fixing it. It read
as a broken movement path: the client log went silent at the join line and nothing moved for two
minutes. It passed standalone and failed in the suite — a reproduction that depends on how fast the
box is, inside a harness, is usually the harness racing the thing it watches.

**The first fix passed for the wrong reason.** It gated client readiness on the page's
`__omwUiHold`, on the theory that an overlay was holding the controls. s22 went green — but the
run's own log said `a UI hold is still up after 15s` for every client, so the hold never dropped at
all and the "gate" was a 15 s sleep in a gate's clothes: it bought one pass and charged every other
scenario 15 s per client. Reissuing the command until it takes needs no theory about what the box
is doing and no number guessed in advance.

### A test-infrastructure trap, recorded so it is not re-diagnosed as a product bug

The first re-run after the fix reported `0 passed, 2 failed` in 0.4 s per scenario. The cause was
not the product: the harness's Linux `node_modules` volume had been refilled with a plain
`npm ci`, and the peer image sets `NODE_ENV=production`, so npm installed the three runtime
dependencies and **silently omitted esbuild**. The harness's in-container `npm run build` then
died with `ERR_MODULE_NOT_FOUND` and every scenario failed instantly. Refill that volume with
`npm ci --include=dev`. An instant, uniform failure across unrelated scenarios is an
infrastructure signature, not a regression.

## Pass 4 - the two the peer-outage scenario was hiding

s69 failed at a different step on almost every run, which read as flakiness and was not. Each
fix uncovered the next fault behind it. Both of these are ORDINARY-PLAY bugs that a live peer
was masking; the outage only stripped the stream down far enough to see them.

| Severity | Bug | Fix |
|---|---|---|
| high | **A puppet gave up mid-stride.** The server relays a pose only when it CHANGES, so a player who stops walking stops generating updates — and `puppet.lua`'s idle guard zeroed the puppet's controls one second later, abandoning it wherever it stood. Measured end to end: the walker moved 102 units, the puppet **received the correct final pose**, walked 17 of them, and stopped 85 short — permanently, until that player moved again. **This happens at the end of every walk in normal play.** | An idle stream now lets the puppet FINISH closing on the newest pose it holds and parks it on arrival. Nothing to run away toward (the target is fixed once the stream stops), and a wedged puppet is still rescued by the stuck detector. |
| critical | **A replacement peer moved every body to the world origin.** The late-joiner cell sync fabricated `x: p.pose?.x ?? 0`, and on the SIM PEER a `PlayerCellChange` is not advice — it TELEPORTS that player's avatar there. The peer log said it outright: `avatar #2 follow-teleport to (0,0,0) ok=true`. The avatar then streams AUTHORITATIVE poses from the middle of the world, so the owner is dragged along. | The server never invents coordinates (an unknown pose is announced on that player's next move); the client treats a cell change with no usable position as cell information only, never a teleport order. |
| high | **A peer replacing a dead one held cells with an avatar for nobody.** `syncStateOnJoin` hands a peer everyone's character when the PEER joins — before it holds any cell — so a restart filed the docs and spawned nothing. | `pushAvatarsToPeer` re-pushes at the world-peer flip, beside the cell release. |

**How they were found, which is the reusable part.** The `puppets` mirror reads the puppet
OBJECT's position, so it cannot distinguish "the batch never arrived" from "it arrived and the
puppet did not act on it" — two faults with opposite fixes that look identical. A protocol
observer (`TestClient` from `testpeer.mjs`) attached beside a browser client settles the
server's half in one run: it saw the walker's pose relayed correctly while the browser's puppet
sat frozen, which exonerated the server and the whole fan-out at a stroke. Counters in
`global.lua` (`moveRx`) and `puppet.lua` (`puppetRx`) then pinned the remaining hop. Both
mirrors were kept.

**A unit test now covers the transition** (`inputauthority.test.ts`): every existing test in that
file ran with the peer ALIVE, so nothing checked that a client-authored move still reaches other
players once the peer stops. A player who can move but whom nobody can see move is not
meaningfully unfrozen.

## Still open — conscious decisions, not defects (all recorded in STATUS.md)

- **Progression stays client-asserted** (attributes/skills/level/spells/inventory counts). The
  client is the right asserter for use-based progression; the peer owns combat/positions/item
  state. The plan's `identity.lua` "reversal" waits on the discrete-intent tier.
- **Discrete-intent request→result tier** (equip/cast/activate/barter/take) and **inventory
  request→result** — need a *vetoing* engine hook; `OnItemTransferred` is notify-only.
- **`mwmp/puppets.*` + the generalised damage veto (E5)** — poison/disease/fall/drowning still
  use the bespoke `isPuppet` path; deleting it needs the general veto first.
- **Phase 2 engine generalisation** — `Actors::rest(actor)`, `updateCrimePursuit`, levelled-list
  nearest-avatar policy, difficulty scaling, non-GUI level-up trigger. A peer avatar with a
  bounty is not pursued and cannot level. Bounded engine work, not authority.
- **The plausibility envelope** (connection.ts) is still live; harmless with input authority,
  retire when the intent tier lands.
